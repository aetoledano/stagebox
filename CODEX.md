# Project Guide

## Summary

This repository is a Wails v2 desktop launcher named `launcher`, branded in the UI as `StageBox`. It is built as a kiosk-style game launcher with a Go backend and a Vite-powered vanilla JavaScript frontend.

The app loads local games from a configured game root and fully installed games from Steam libraries, renders them as a fullscreen controller-friendly grid, launches selected game executables, hides/restores the launcher window around game sessions, and provides Windows kiosk helpers such as fullscreen mode, Bluetooth status/pairing, Steam session launch, display resolution setup, wallpaper hosting, shell registration, shutdown, and restart.

The project is Windows-focused at runtime, but many platform-specific tools have non-Windows stubs so parts of the code can still compile or be inspected on Linux.

## Main Layout

- `README.md`: public-facing project documentation for GitHub. Keep install, usage, game metadata, feature list, troubleshooting, and publishing/license notes in sync with user-visible behavior.
- `main.go`: Wails entry point. Embeds `frontend/dist`, loads `config.json`, extracts embedded runtime assets, binds `App`, and starts Wails.
- `app.go`: shared `App` state and lifecycle, game loading/launching, hardware status events, and controller/keyboard bridge helpers.
- `game_options.go`: Wails `GetGameOptions`/`SetGameVirtualInput` native-only card settings, idle-session write guard and `game:options-changed` events.
- `actions.go`: Wails-bound system actions (shutdown/restart/exit), Bluetooth pairing flow and process/window helpers, launcher input-pause controls, and Wi-Fi scan/connect API.
- `steam_guide.go`: bounded idle-launcher PS/Guide event owner, verified Steam foreground recovery and controller-pointer handoff for visible Steam prompts.
- `steam.go`: Wails-bound `OpenSteam` action, installed-Steam client session flow, card config/internet/update preflight, ID/phase-checked `SteamLaunchAction` update choices and `SteamUpdateStates` polling API, executable discovery wrapper, and installer download/start helpers, including the installer URL. Shared Steam discovery lives in `internal/games`; `focusAfterSteamSession` settles native foreground ownership after both Steam game card and topbar Big Picture sessions.
- `retrobat.go`: Wails-bound `OpenRetroBat`, installed frontend session handoff, and Steam-style official installer download/start helpers. Shared install discovery and native session tracking live in `internal/games/retrobat_*`.
- `assets`: root-level project assets. `loading-space.png` is the embedded Space Launch native fallback wallpaper; `loading.jpg` remains a legacy source. `app-icon.png` is the default StageBox executable icon source, with `app-icon-2.png` retained as an alternative.
- `output`: retained launch-panel/background design previews, artwork source and generation prompts; runtime artwork is embedded from `assets` or imported from `frontend/src/assets/images`.
- `build/appicon.png`: ignored Wails executable icon input. The Makefile `app-icon` target copies it from `APP_ICON` (default `assets/app-icon.png`) before Wails builds, then Wails regenerates the Windows icon resource during `make build-win`/`make release`.
- `internal/assets`: runtime asset helpers, including embedded asset extraction, thumbnail cache path, and Wails thumbnail HTTP handler.
- `internal/config`: JSON config shape. Currently `gamesRoot`, `debug`, optional `retrobatPath`, and `downloadControllerDatabase` (default true, refresh each Windows startup).
- `internal/games`: game metadata model, concurrent local/Steam library loader, thumbnail generation/cache support, launch/kill tracking, and Steam session launching.
  - `native_config.go`: strict fresh native `lc.json` reads and flag-only atomic saves, preserving original relative paths and unrelated JSON values. `native_config_test.go` adds preservation and rejection coverage; not run.
  - `steam_discovery.go` plus `steam_discovery_windows.go`/`steam_discovery_stub.go`: Steam executable/environment/registry discovery, library folder enumeration, installed manifest validation, stable AppID-based UUIDs, and launch-time revalidation.
  - `launch_window_windows.go`/`launch_window_stub.go`: local-game window readiness for the shared launch screen. Uses job membership for advanced games, existing descendant tracking for process-tree games, and the root PID for ordinary process mode. Non-Windows falls back to process startup.
  - `steam_config.go`: generated AppID-based `gamesRoot/SteamGames/<AppID>-lc.json` defaults, strict manual overrides, conservative uninstall cleanup, and immutable per-launch config preparation. `steam_config_test.go` covers preservation, reload, ownership and cleanup; added, not run.
  - `steam_update.go`: Steam manifest update flags/64-bit byte counters, phase-aware launch feedback and update icon data. Generic UpdateStarted/UpdateRunning without transferred bytes shows preparing; partial download bytes with generic flags expose download progress; once the download is complete, partial staging bytes expose installation progress instead. Explicit Downloading uses its totals. Download completion alone is not installation completion. `steam_update_test.go` covers state/counters/identity; added, not run.
  - `steam_interactive.go`/`steam_interactive_windows.go`: shared Steam card UI/game handoff and the separate download-only action. Every game activation uses `Steam.exe -gamepadui -fullscreen steam://run/<AppID>` exactly once; update-only uses library navigation without queuing Play. Native UI sampling only observes activity and never launches a game. `steam_interactive_test.go` covers exact command selection, update-only separation, long UI/dialog lifetime, bounded invisible startup, handoff, active-update validation and config preservation; added, not run. Silent readiness/recovery, first-run hints and rescue paths have been removed.
  - `steam_vdf.go`: bounded text KeyValues parser for Steam library/manifest files, including nested objects, comments, quoted names, and escaped Windows paths.
  - `steam_appinfo.go`: offline app type and controller metadata reader for binary appinfo versions 39, 40, and 41 (including the shared string table).
  - `steam_artwork.go`: local Steam artwork lookup (flat, per-app, and content-hash layouts), bounded CDN download/cache fallback, and existing JPEG thumbnail generation.
  - `steam_game_tracking.go`, `steam_game_windows.go`, and `steam_game_stub.go`: portable Steam game startup/handoff timing and Windows game-only Job Object/handle tracking. This path is separate from the whole-client Steam topbar session.
  - `steam_guide_windows.go`/`steam_guide_stub.go`: retained same-install/session process monitor for uninvited Steam foreground UI; no Steam activation/config edits, visible-dialog dismissal or process termination.
  - `steam_session_windows.go`: native Steam/Steam webhelper window activity detection, including current/legacy Big Picture identity, minimized-window exclusion, and handle-verified game windows.
  - `steam_ui_windows.go`/`steam_ui_stub.go`: bounded Steam session return cleanup plus minimized-only handoff cleanup; hides verified same-session client UI, closes existing Big Picture through Steam on return, and performs cancellable asynchronous settling while retaining the client. Game-card owners preserve setup UI, then repeat minimized-only sweeps briefly after the first real game window.
  - `steam_library_test.go`, `steam_game_tracking_test.go`, and `steam_game_windows_test.go`: focused library/metadata/artwork, timing/path, and game-only job/kill coverage; added but not executed.
- `internal/jsonx`: strict JSON file loader used by config and game metadata loading.
- `internal/logx`: small logging package with file/stdout support and panic recovery. Appends across restarts and rotates logs of at least 8MiB to one `.previous` backup at startup; a long single run can exceed that size. Initialization logs the absolute log path. `main.go` always enables DEBUG logging; `config.debug` only controls exit behavior.
- `internal/platform`: platform integration packages. Windows files contain Win32/PowerShell integrations; `*_stub.go` files keep non-Windows builds safe.
  - `audio`: native Windows render-endpoint selection, master volume, and mute through a CGO/C++ Core Audio bridge.
  - `bluetooth`: Bluetooth state, bring-up, and connected-device detection.
  - `controller`: SDL3-first normalized controller polling with XInput/WinMM fallback, launcher keyboard hook, and Wails input events. `launcher_focus_windows.go` finds the exact StageBox window and reclaims native foreground focus; the non-Windows controller stub supplies its fallback.
  - `cursor`: cursor visibility helpers.
  - `display`: display resolution selection.
  - `network`: `internet.go` checks actual internet reachability for Steam cards with parallel bounded HTTP probes; `internet_test.go` covers captive portals, redirects, fallback and cancellation (not run).
  - `shell`: per-user shell registration.
  - `wallpaper`: native wallpaper host.
  - `wifi`: Windows WiFi scanning and connection helpers backed by `netsh wlan`.
  - `winapi`: shared Windows DLL handles.
- `frontend/src`: vanilla JS frontend modules and CSS.
- `frontend/src/features`: frontend feature modules for Bluetooth, clock, and controller navigation. `launchFeedback.js`/`css/launchFeedback.css` provide checking/update/startup feedback and controller/keyboard-dismissible errors; controller routing gives this modal priority. `assets/images/update-ico.svg` is the white vector update indicator before card titles.
- `frontend/wailsjs`: generated Wails bindings used by frontend imports.
- `tools/hidmaestro`: `Program.cs` elevated multi-controller helper, `HidHide.cs` filter-driver setup/control/owned settings and recovery, `LICENSE-HidHide.txt` verbatim MIT license, `StageBox.HIDMaestro.csproj` self-contained Windows x64 publish, `Directory.Build.props` isolated intermediates, `prepare.py` pinned upstream SDK/installer bootstrap and published integrity manifest, and `README.md` provenance/build/lifecycle details. Binaries, runtime and downloaded SDK/installers are ignored under `build`; do not commit them.
- `custom_scripts`: Windows kiosk helper scripts. `install-stagebox.ps1` owns elevated machine setup, with `install-hidhide.ps1` as its shared standalone/idempotent HidHide driver step; `svc.vbs` owns the hidden StageBox shell loop, `systemsvcs.ps1` service/adapters priming, and `elevated-PS.cmd` manual elevated testing.
- `vendor`: committed Go vendor tree.

## Runtime Data Flow

### RetroBat frontend session (step 1)

- `retrobat.go` exposes `App.OpenRetroBat`, reached by the RetroBat-logo topbar button in `frontend/index.html`/`frontend/src/main.js`. Existing topbar controller/keyboard routing discovers the button automatically. The button loads `frontend/src/assets/images/retrobat-ico.svg` in a 24×24px box alongside Steam's `steam-ico.svg`. RetroBat preserves its original silhouette proportions with a square `viewBox="24 11 234 234"`, adding 11 source units of transparent space on each side of the original viewport. Both icons use `object-fit: contain`; their topbar buttons stay 36×36px and image boxes 24×24px. Do not stretch the RetroBat artwork: the user rejected the widened variant. The global Steam button and Steam cards both use the white vector SVG, not the legacy user-provided `steam-ico.png`. This white vector logo was traced from the user-added `retrobat.jpeg`: dark silhouette becomes white, the white background becomes transparent, and the D-pad/four round button cutouts remain transparent. The silhouette uses smooth cubic paths and cleaned geometric controls with an even-odd fill; it contains no embedded raster. Preserve the JPEG as the source reference. No runtime session/input behavior is changed by this icon.
- `internal/config.Config.RetroBatPath` maps to optional `config.json` `retrobatPath`, accepting the install folder or full `RetroBat.exe` path. Config is startup-owned; restart StageBox after edits. No per-game `lc.json` fields are added for this step.
- `internal/games/retrobat_discovery.go` resolves explicit config, then `RETROBAT_PATH`, then fresh Windows installation records/local-drive roots, the system-drive `RetroBat` folder (normally `C:\RetroBat`), Program Files/Local AppData, a `RetroBat` folder beside StageBox, and `PATH`. Explicit config/environment paths remain authoritative and avoid automatic enumeration. `ErrRetroBatNotFound` distinguishes a missing install (including a not-yet-created configured directory) from malformed executable names or access errors; only missing installs trigger setup. Paths are made absolute, checked for a regular executable, and run with the install directory as working directory. No ROM importer or writes to RetroBat settings are introduced. Official entry point reference: https://wiki.retrobat.org/get-started/installation-and-first-startup.
- `retrobat_discovery_windows.go` implements `retroBatPlatformPaths`: read HKCU/HKLM App Paths and RetroBat-named uninstall entries in both 32/64-bit views, using `InstallLocation` or the directory of parsed `DisplayIcon`/`UninstallString`; expand registry environment variables. Then use `GetLogicalDrives`/`GetDriveType` to check `<drive>:\RetroBat` on fixed/removable local drives, including the user's `D:\RetroBat`. No registry values are written and no uninstall commands are executed. Shared discovery skips stale/duplicate/empty paths and validates `RetroBat.exe`. `retrobat_discovery_stub.go` supplies no platform candidates on non-Windows. Re-read on every button activation rather than caching a pre-install miss; do not recurse disks or probe network/CD drives.
- Installer helpers in `retrobat.go` implement the Steam-style missing-install flow: resolve the official repository's latest stable release via GitHub's unauthenticated API, select a positive-size `RetroBat-*-win64-setup.exe` HTTPS asset under `RetroBat-Official/retrobat/releases/download`, download to a unique temporary file, validate exact release size and `MZ` header, then promote to `cache/installers/RetroBatSetup.exe`. Release lookup is bounded to 20 seconds/2MiB and download to 30 minutes, both context-cancellable. No cached file is executed after a failed download. Downloads report throttled percentage through the existing feedback modal with stage `installer`; `launchFeedback.js` labels it RetroBat setup. Start directly, fall back to `explorer.exe` for elevation just like Steam, and reap those request processes asynchronously. The session guard blocks concurrent downloads; StageBox remains visible and cursor is shown for setup. Installation is interactive and independent of game/session tracking, with no automatic RetroBat launch afterward. Discovery refreshes on the next button press; unregistered portable/custom locations outside the searched folders require `retrobatPath` on the next StageBox startup. Source: https://www.retrobat.org/en/download/ and https://docs.github.com/en/rest/releases/releases#get-the-latest-release.
- `internal/games/retrobat_session_windows.go` uses the existing suspended-start Job Object primitive to capture wrapper-to-EmulationStation/emulator children before they run. It has its own completion loop over native job membership every 250ms, ending only when the group is empty; minimized/hidden ES and long windowless gameplay cannot trigger the local-game visibility timeout. Root command completion is not session completion. Three consecutive membership query failures report an error. `retrobat_session_stub.go` returns an explicit unsupported error on other platforms. Context cancellation closes handles without terminating RetroBat.
- The App session guard is retained through return. Launcher controller/keyboard navigation is paused, StageBox hides, the normal cursor is restored/parked, then completion/error clears the existing feedback UI before fullscreen restore, native focus settling, cursor hiding and input resume. Discovery errors stay visible and use `game:launch-blocked`; start/tracking errors use `game:launch-error` plus acknowledged `game:end` before return. Existing Steam and native game paths are unchanged.
- Traps: do not route this through `jobGameProcess.Wait`, whose visible-window quiet period is for local games. Do not register RetroBat as `curProcess`: RetroBat owns emulator exit controls and StageBox's Start+Back kill must not terminate the whole frontend. Helpers surviving ES keep this whole-process-group session alive. External brokers/elevation/breakaway may evade job inheritance. An already-running same-install RetroBat/ES is rejected after exact-path/current-Windows-session checks, because a singleton handoff would escape the newly created job. Do not claim existing-instance attachment or universal emulator tracking. No kill-on-close job policy is set.
- The user accepted the RetroBat addon as completed. Steps 2 and 3 are described below. Virtual input starts off for unknown controllers, can be saved as a per-controller default for native games/Steam/Steam cards/RetroBat or additionally enabled for a native game.
- `internal/games/retrobat_discovery_test.go` covers folder/executable/quoted paths with spaces, explicit-path failure without fallback, config-over-environment precedence, invalid authoritative environment paths, missing-install versus config-error classification, stale automatic candidates followed by an installation appearing on another drive, and quoted/unquoted registry icon/uninstaller path parsing. Tests are not run; ask the user to run them.

### SDL3 controller backend (step 2)

- `App.pad` is now `*controller.ControllerBridge`, started by `StartControllerBridge(ctx, volumeAction, downloadDatabase)` using `config.DownloadControllerDatabase`, with an optional nonblocking Guide callback carrying the source profile ID. The former XInput-specific bridge name was replaced in Windows and non-Windows stubs; existing pause/resume, pairing, pointer, game key-map, stop, focus and `pad:*` contracts remain. The Windows bridge owns a child context cancelled by `Stop`, also bounding its background startup refresh (enabled by default). Frontend input routing and game/Steam/RetroBat launch adapters are unchanged.
- `internal/platform/controller/sdl_windows.go` binds the small required SDL3 API surface through existing `x/sys/windows` DLL calls, without adding Go modules, CGO or an SDL window. Only `SDL_INIT_GAMEPAD` (which implies joystick/events) is initialized. One dedicated locked OS thread calls `SDL_SetMainReady`, initializes, pumps/reads state every 8ms, discovers/open pads every 250ms, and closes pads/quits/unloads SDL. SDL's source designates the first `SDL_SetMainReady` caller and event-init thread as its main/event thread; keep all lifetime/pump calls on this owner. No video/audio SDL subsystem is started. References: https://wiki.libsdl.org/SDL3/SDL_PumpEvents and https://github.com/libsdl-org/SDL/blob/release-3.4.18/src/SDL.c.
- `sdl_runtime_windows_amd64.go` embeds the unmodified official `sdl/windows_amd64/SDL3.dll` and `LICENSE.txt`. Existing `internal/assets.ExtractEmbeddedFile` extracts `cache/assets/SDL3-3.4.18-amd64.dll` and `SDL3-3.4.18-LICENSE.txt`, refreshing changed bytes. Load only the absolute extracted DLL using `LoadLibraryEx` restricted to its directory/System32. Other Windows architectures use `sdl_runtime_windows_other.go` to select legacy input; non-Windows remains a no-op controller stub. Deployments still need only StageBox's executable, not another SDL installation. `sdl/README.md` records release URL, official archive/dll digests, zlib licensing and update instructions; the downloaded archive digest was verified and native exports/imports inspected without executing the DLL. The 25 bindings, including physical-path identity, mapping/inventory diagnostics and `SDL_IOFromConstMem`, are verified against shipped native exports; static imports are Windows system DLLs and no extra CRT DLLs are required.
- `gamepad_state.go` retains the existing 12-byte XInput-compatible state layout/button masks as the internal normalized representation, also sent to the opt-in virtual helper. Convert SDL physical south/east/west/north to A/B/X/Y, invert both vertical axes with signed-min saturation, scale released-to-full triggers from 0..32767 to 0..255, and keep Guide/extended buttons out of the normalized payload. SDL tracks Guide edges separately for the idle-launcher Steam UI guard below. This preserves existing deadzones, directional repeat, volume, key/mouse maps and Start+Back semantics. Nintendo's bottom B is the launcher's A action; printed labels are not swapped into Xbox position semantics. SDL also retains its built-in/environment mapping support.
- `sdl_database_license_windows.go` embeds only the verbatim upstream `sdl/gamecontrollerdb-LICENSE.txt` bytes, copied beside the downloaded database. There is no embedded StageBox mapping subset or mapping cache extraction. The former `sdl_mappings_windows.go`, repository `sdl/gamecontrollerdb.txt`, `bundledSDLMappingPath` and file-IO mapping loader have been removed. Old `cache/assets/stagebox-gamecontrollerdb-v1.txt` and its companion license are unused and never recreated; existing copies may be deleted. SDL's built-in mappings remain inside its DLL. The Ultimate Windows `2dc8:3012` profile is already in the current full upstream database, so it requires no separate embedded profile.
- `controller_database_windows.go` refreshes the upstream database on every Windows startup in a separate Go goroutine. `config.NewConfig` defaults `downloadControllerDatabase` to true; explicit false disables HTTP but still prepares/loads/watches local mappings. Immediately use cached/local or SDL built-in input while fetching the fixed HTTPS raw SDL_GameControllerDB master URL into `<exe-dir>/assets/gamecontrollerdb.txt`. Validate a bounded 30-second/context-cancellable HTTP 200 response (8MiB, exact declared length, UTF-8/row structure including SDL's special `xinput` GUID, Windows profiles) before writing/syncing a unique same-directory temporary file and atomic `MoveFileEx` with `REPLACE_EXISTING`. Identical content skips rewriting/reload. Failure preserves the cached base; no network work runs on the UI or SDL owner thread and no recurring request during the session. Stop cancels the request. Prepare the upstream license alongside only if missing.
- Manual edits belong in `<exe-dir>/assets/gamecontrollerdb-overrides.txt`, automatically prepared as an empty commented template only when missing and never overwritten. Before the first changed local-base replacement, preserve its bytes in `assets/gamecontrollerdb-before-refresh.txt` only if that backup is absent so edits made under the earlier shared-file policy can be migrated. Only the managed base is replaced. Paths are executable-relative, not runtime cache/Vite assets. `controllerDatabasePathsIn` orders managed base, legacy `<exe-dir>/gamecontrollerdb.txt` overrides, then primary assets overrides; SDL built-ins/environment load before this stack. Primary overrides therefore remain final across upstream refreshes.
- The SDL owner checks all three bounded validated external snapshots/SHA-256 every second; two identical changed snapshots trigger live reload (normally 1–2 seconds), including downloads, manual edits, creation/deletion and same-size/time changes. UTF-8 BOM is stripped before SDL loading; Windows rows require `platform:Windows`. Invalid/unreadable changes retain prior mappings with deduplicated errors. SDL loading is additive, so close handles/quit/reinitialize this private SDL input backend and reapply all current sources to restore deleted overrides. Rescan selection; increment `mappingRevision` and reset held mapped outputs/repeat/volume/kill/neutral state even for reused IDs. Keep snapshot bytes alive through synchronous `SDL_IOFromConstMem`/load/close. Failed SDL reload restores the previous snapshot or falls back if restoration fails. Normal game input remains independent; opted-in virtual reports use the reloaded physical mapping. Logs distinguish `source=database` and `source=overrides`; no `source=fallback` file is loaded.
- `controller_database_windows_test.go` covers real base/override source order, HTTP refresh of existing bases, preserving separate/concurrently created overrides and backup creation, failed/empty/malformed/non-Windows/oversize responses retaining the cached base, temp cleanup, BOM/content changes and deletion detection. Tests are not run; ask the user to run the Windows controller suite and verify real startup refresh/live reload.
- Discovery diagnostics enumerate SDL joysticks (including unmapped devices) and log name, VID/PID and `mapped` on connection/status changes; this auxiliary inventory does not change controller counts, selection or fallback policy. Opened gamepads log the complete `SDL_GetGamepadMapping` result, freed with `SDL_free`; this identifies the matched GUID/Start/Back bindings. All calls remain on the locked owner thread. Native XInput controllers are read through SDL for StageBox; games read physical input independently. Opted-in native-game forwarding is described in step 3.
- `SDL_JOYSTICK_ALLOW_BACKGROUND_EVENTS=1` is deliberate: Wails is not an SDL window and existing mapped gameplay, pairing/pointer helpers and kill shortcut need background reads. Launcher navigation/right-stick volume remain gated by exact StageBox foreground ownership and pause state. Steam cards retain their configured key maps/dialog helpers; Steam/RetroBat now also forward Virtual-default controllers through the same normalized virtual-input bridge, without a native per-game override.
- Keep SDL and native sampling exclusive per navigation frame. If SDL runtime/setup fails, use the existing XInput/WinMM backend. Three consecutive SDL enumeration failures close it and switch to native; absent mapped SDL gamepads allow the prior raw joystick fallback. `STAGEBOX_CONTROLLER_BACKEND=legacy` bypasses SDL for troubleshooting. SDL tracks/open pads by instance ID and retains the first selected connected controller until it disconnects. Native source/slot and SDL IDs use distinct internal identities so a backend switch cannot inherit button edges.
- Device changes/disconnection release mapped keyboard/mouse outputs without deleting game bindings, reset repeat/volume/kill/previous state, and require a fully neutral replacement pad before accepting input. Game-map configuration and output processing share the existing mutex, including mouse parameters. `Stop` is idempotent; context/quit ends polling and closes SDL resources on the owner thread. `ConnectedCount` now reads an atomic poller-owned snapshot instead of calling native/SDL APIs from hardware-status goroutines. Counts include opened mapped SDL pads while SDL is active, or the existing native inventory when fallback is selected; don't sum both and duplicate the same device. Separate virtual devices exposed by Steam Input/other drivers may still appear as distinct inventory entries; do not claim universal duplicate-device correlation. Virtual-input sessions route independent converted pads as described below.
- `gamepad_state_test.go` adds portable checks for physical button chords/ignored Guide, signed axis/trigger endpoints, native payload size, stable selection/removal, held-button replacement neutral rearm and trigger/stick neutrality. `sdl_windows_test.go` adds a Windows amd64 smoke check for extracting/loading/initializing/pumping/closing the shipped SDL DLL and consistent native inventory, on one locked thread, without Wails or injected input; no physical pad is required and it uses the normal writable runtime cache. Tests are not run. User should run the controller suite on Windows and validate real-device hotplug/mappings, held disconnect/reconnect, game returns, Steam Input coexistence and the legacy override before step 3.

### Controller defaults, selection and mapping test

- `controllers.go` exposes `GetControllers`, `SetControllerDefault`, `SelectController` and `TestController`. Session locking prevents changing defaults/selection or starting tests during games. `controller_inventory_windows.go` publishes immutable SDL snapshots, queues source selection for the owner, emits `controllers:update` every 250ms and normalized `controller:test-state` every 32ms while testing. Non-Windows methods return unsupported/empty results. No Wails API calls SDL from its request goroutine. Private `prepareSessionVirtualInput`/`finishSessionVirtualInput` helpers reuse saved controller routing and helper startup/teardown across App game launch, topbar Steam and RetroBat. Setup runs before consumer launch/hide; failures block launch. Teardown completes before launcher input resumes, including launch failures and RetroBat context cancellation. Steam UI is backgrounded before restoring physical visibility. Steam and RetroBat pass false for the native per-game override. No new controller preference or mapping editor is introduced.
- `controller_settings.go` owns controller identity, persistent profiles, routing policy and diagnostic conversion. `<exe-dir>/assets/controllers.json` is user-owned version-1 JSON, containing a map of 32-hex IDs to name, connection, mode (`native`/`virtual`) and optional `nativeXInput`. It is separate from the managed controller mapping database and recovery journal. Hash VID/PID + connection + reported serial, falling back to lowercase physical interface path; never persist SDL instance IDs. USB/Bluetooth modes can have separate profiles. Pads without a useful serial may need another choice after a port/path change; no universal physical identity merge is claimed. Native `XInput#` sources are automatically Known Native and cannot be converted, including saved disconnected entries.
- Bounded strict profile loading rejects corrupt/unknown-version input and keeps it untouched; navigation remains Native and saving returns an error. Saving serializes writers, prepares/syncs/replaces a temporary file outside the short in-memory mutex, then publishes the new map. Preserve this file when deploying; never package a developer's preferences. Connected pads and saved disconnected profiles both appear in the menu. Manual JSON edits take effect after restarting StageBox.
- `frontend/src/features/controllers.js`, `css/controllers.css` and `assets/images/controller-test.svg` provide Start/Tools → Controllers, Native/Virtual choices, saved disconnected entries and a live generic controller diagram. Names carry a derived short `#ABC123` ID in the list/settings/test; start with six hash digits and extend by two until unique among current/saved profiles. A tag tooltip exposes the full ID. This is identification, not a player/XInput slot number. An unknown mapped non-XInput pad prompts when StageBox is focused, no other menu/pairing/game is active. Later postpones until the next connection. Saving a choice suppresses future prompts for that identity. Prompts are deferred during Steam/RetroBat/native sessions; `pairing-ui:start/end` suppress them during Windows pairing. Selecting a connected entry selects that pad for navigation, with the existing neutral rearm.
- The mapping test displays empty face-button circles by normalized position (readout South/East/West/North), Back/Start, shoulders, D-pad, stick clicks, moving sticks and trigger levels. The silhouette follows the user-supplied asymmetric-pad reference; lower controls and labels stay inside the shell. Stick centers/travel live in SVG `data-center-x/y` and `data-travel` attributes, read by JS; cap displayed displacement radially so diagonals stay inside their rings. Do not reintroduce duplicate hard-coded JS coordinates or printed A/B/X/Y letters. It disables launcher keyboard/controller actions so presses do not launch, navigate, adjust volume or invoke the kill chord. Hold Start+Back for one second, mouse Back or keyboard Escape returns to settings; individual controller buttons remain test input. Ending the test or launching a game clears the backend test flag and rearms input. Generation checks prevent async UI work reopening a closed panel.
- User-selected routing rule: Virtual-default non-XInput pads convert in native games, topbar Steam sessions, direct Steam card launches (including update-only UI) and RetroBat sessions. `enableVirtualInput=true` additionally converts Native-default non-XInput pads; false restores only those pads to Native. The game switch never disables Virtual-default pads and native XInput always bypasses. No additional per-game controller-ID overrides. Steam/RetroBat use only saved controller defaults (`gameEnabled=false`), with no per-game setting or native game-switch inheritance. Unknown pads behave Native until configured (or the game switch is on). Session setup snapshots the connected roster; preference changes are blocked until return.
- The SDL owner reads every mapped physical pad. Only the selected pad drives existing launcher/key/mouse/kill actions; independent states feed each converted target. Profile/diagnostic/virtual routing requires the SDL backend; legacy XInput/WinMM fallback remains navigation only. `controller_settings_test.go` adds routing, independent persistence, reconnect identity and invalid-file preservation coverage; tests were not run.

### Idle-launcher PS/Guide Steam UI guard

- User reports the DualSense PS button opens Steam firmware-update prompts or a minimized Steam library that steals launcher input until Alt+Tab/mouse dismissal. ### Main startup and game-card flow

1. `main.go` creates a default config and overlays `config.json` with `jsonx.LoadJSONFile`.
2. `main.go` extracts embedded runtime assets, including `assets/loading-space.png`, to `cache/assets` because the native Windows wallpaper host needs a filesystem path.
3. `NewApp` stores the config and Wails binds the `App` instance.
4. On startup, `App.startup`:
   - saves the Wails context,
   - tries to register the launcher as the per-user shell on Windows,
   - tries to set the primary display to the highest enumerated mode so games can use the monitor's native/max resolution,
   - starts a native wallpaper host for the extracted embedded `loading-space.png`,
   - starts the SDL3-first controller bridge and Windows keyboard bridge,
   - starts Bluetooth status polling,
   - fullscreenes the Wails window.
5. `frontend/src/main.js` creates an empty grid, initializes controller navigation, subscribes to game loading events, then calls `LoadGames`.
6. `LoadGames` discovers local game directories and fully installed Steam manifests across `libraryfolders.vdf` roots, synchronizes editable Steam configs under `gamesRoot/SteamGames`, then uses one 8-worker pool for both sources. Local workers parse `lc.json`; Steam workers resolve Steam artwork. Each worker creates/reuses a 1280px thumbnail under `cache/thumbnails` and emits `game:loaded` when the card is ready. Steam discovery still runs when the local game root is empty or unreadable. Loading progress includes both sources and worker callbacks are serialized so counts stay monotonic.
7. Cards use `/game-thumbs/<game-id>-<hash>.jpg` URLs served by the Wails asset handler instead of base64 image payloads.
8. Activating a card calls `Launch(id)`. Steam preflight claims the session guard, emits `game:launch-begin`, re-reads manual config, validates the existing installed card and checks internet. All Steam games send one `Steam.exe -gamepadui -fullscreen steam://run/<AppID>` activation, with no client registration gate, bootstrap, restart recovery or separate Big Picture opening. First-run and known games share that path; Steam owns setup/update/game startup order. A known update offers Open in Steam (update then Play), Update in Steam (download-only) and Back before input pause or launch lock. Download-only opens the game page; the user selects Steam’s Update button, then can exit Big Picture while the download continues. No Play is queued in that mode. Both launch actions clear panel buttons and show “Launching Steam…” until native Steam UI/game handoff. `game:steam-ui-ready` clears/acknowledges the panel before Steam UI handoff; `game:window-ready` separately acknowledges the selected game’s first real window. Steam cursor/mappings apply at that real game window. Big Picture/dialog lifetime controls waiting before a game appears; afterward game-only tracking controls completion. On completion/error, bounded Steam UI cleanup runs, `game:end` is acknowledged before showing fullscreen StageBox, foreground is reclaimed, input resumes and the session guard is released. Local games and the global topbar Steam session retain their prior behavior.

## Game Metadata

Local games are discovered by scanning immediate subdirectories of `config.gamesRoot`. Each local game directory must contain `lc.json`. Installed Steam games are discovered automatically. The launcher creates editable `SteamGames/<AppID>-lc.json` files under `gamesRoot` on first discovery; that reserved folder is excluded from local directory scanning.

Expected fields map to `internal/games.GameData`:

```json
{
  "executable": "Game.exe",
  "args": ["-fullscreen"],
  "startsOn": ".",
  "image": "cover.jpg",
  "name": "Game Name",
  "description": "Optional description",
  "controls": 2,
  "trackMode": "processTree",
  "advancedTracking": false,
  "waitAfterExitSeconds": 1,
  "showCursor": false,
  "enableVirtualInput": false,
  "delayedKey": {
    "seconds": 4,
    "key": "Enter"
  },
  "keyMap": {
    "mouse": "rightStick",
    "mouseSensitivity": 14,
    "buttons": {
      "A": ["Space", "Enter"],
      "B": ["Escape"],
      "L3": ["Shift"],
      "R3": ["E"],
      "LT": ["MouseRight"],
      "RT": ["MouseLeft"],
      "DPAD_UP": ["Z", "ArrowUp"]
    },
    "leftStick": {
      "up": ["W"],
      "down": ["S"],
      "left": ["A"],
      "right": ["D"]
    }
  }
}
```

Notes:

- `id` is optional in JSON. If omitted, the loader creates a deterministic UUID from the game name, falling back to the game directory name when the name is blank. If `id` is supplied, it must be a valid UUID.
- JSON decoding is strict. Unknown keys fail because `jsonx.LoadJSONFile` uses `DisallowUnknownFields`.
- `executable`, `image`, and relative `startsOn` values are resolved relative to the game directory. If `startsOn` is omitted, the working directory defaults to the game directory.
- `args` is optional and passes command-line arguments directly to the launched executable.
- `trackMode` is optional. Omit it or use `process` for the original behavior where the session ends when the started executable exits. Use `processTree` for games whose configured executable is a launcher/bootstrapper that spawns child game processes; on Windows the session remains active while the discovered process tree has a visible top-level window. This avoids restoring StageBox while a spawned child game is running, but still restores after the visible game window closes even if helper child processes stay alive. If no visible window appears within the startup grace period, StageBox logs the remaining PIDs and restores.
- `advancedTracking` is an optional boolean, default `false`. On Windows, `true` overrides `trackMode` with the internal `job` mode: create the configured executable suspended, assign it to a Job Object, then resume it so even short-lived launchers cannot race descendant registration. The user's Apache Air Assault metadata can use this flag alongside `delayedKey: { "seconds": 1, "key": "Enter" }` without specifying `trackMode`. The initial PID remains the target for startup focus and the delayed key; key maps/cursor state stay active for the tracked session. Non-Windows builds return an explicit unsupported error for this opt-in flag rather than silently pretending to track a job.
- `waitAfterExitSeconds` is optional. With `process`, it delays restoring StageBox after the started executable exits. With `processTree`, it adds extra delay after the process tree has ended.
- `controls` is optional and drives the card control icons. Use `0` or omit the field for controller-first games, `1` for keyboard/mouse-only games, and `2` for games playable with both controller and keyboard/mouse.
- `enableVirtualInput` defaults false and applies only to native game sessions. The card menu writes it into the original `lc.json`; launch reads it fresh. It requires the paired bundled Windows x64 HIDMaestro helper for non-XInput SDL sources; keep Steam configs separate.
- Images are processed into cached 1280px max-dimension JPEG thumbnails. The frontend receives `thumbnailUrl` and `imageHash`, not base64 image data.
- JPEG, PNG, GIF, WebP, and AVIF source images are supported for thumbnail generation.
- `delayedKey` is optional and intended for games that first open a keyboard-only launcher before the game itself starts. When present, the launcher waits for the game process PID, waits `seconds`, focuses that process window when possible, and sends one keyboard stroke named by `key`. If the process exits before the delay, the key is skipped. Supported key names match the controller key-map keyboard targets, such as `Enter`, `Space`, `Escape`, `Tab`, arrow keys, letters, digits, `Delete`, `F1`-`F12`, and `Numpad0`-`Numpad9`.
- `keyMap` is optional and embedded in `lc.json`. The game key-map path is considered only when the `keyMap` key is present; if it is omitted the controller bridge is fully paused during gameplay as before. `keyMap.buttons` maps discrete gamepad buttons to arrays of key or mouse targets, so one controller input can press multiple targets. `keyMap.leftStick` and `keyMap.rightStick` map stick directions (`up`, `down`, `left`, `right`) to arrays of normal key targets. `keyMap.mouse` can be `leftStick` or `rightStick` to move the OS cursor; `mouseSensitivity` controls X-axis speed from 1-40 while Y-axis speed is intentionally half as fast, with a minimum of 1. If `keyMap` is present but has no valid bindings and no valid mouse stick, launch falls back to paused controller behavior. Supported gamepad keys include `A`, `B`, `X`, `Y`, `START`, `BACK`/`SELECT`, `LB`, `RB`, `LT`/`L2`/`LEFTTRIGGER`, `RT`/`R2`/`RIGHTTRIGGER`, `L3`, `R3`, and `DPAD_UP`/`DOWN`/`LEFT`/`RIGHT`. Supported keyboard targets include letters, digits, `Space`, `Enter`, `Escape`, `Tab`, `Shift`, `Control`, `Alt`, arrow keys, `Delete`, `F1`-`F12`, and `Numpad0`-`Numpad9`. Supported mouse button targets are `MouseLeft`, `MouseRight`, and `MouseMiddle`. See `keypad-sample.json` for a working structured mapping sample.

## Backend Notes

- Wails exposes exported methods on `App` to JavaScript. Keep method signatures simple and JSON-serializable.
- Steam activation trap: all game cards use one combined `-gamepadui -fullscreen steam://run/<AppID>` activation. There is no ActiveProcess/DLL readiness gate, silent bootstrap, automatic client restart, first-run cache or retry/rescue command. Steam owns cold/warm/EULA/update startup; successful command exit does not prove that the game opened. Observe actual Steam UI and the selected game’s native windows/processes. Registry use for executable discovery remains. The global topbar continues to use its independent `steam://open/bigpicture` session.
- Steam executable discovery prefers `STEAM_PATH`/`STEAM_DIR`, then current-user and 32/64-bit machine registry installation paths, then Program Files. `LoadOptions.SteamExecutable` opts the shared loader into Steam scanning. Library paths are deduplicated; both current object entries and older scalar library entries are supported. `GameData.SteamAppID` is the serialized source marker; `steamManifest` stays private and is not exposed to Wails. Steam UUIDs use `launcher/steam/<AppID>` so names/drive moves cannot collide with local UUIDs. These fields are populated by discovery, not manual `lc.json` configuration.
- Steam config defaults are written only with exclusive creation; existing files are never rewritten. Filenames use AppID so title/drive changes preserve edits. Editable fields are `name`, `description`, `image`, `controls`, `showCursor`, `waitAfterExitSeconds`, `delayedKey` and `keyMap`; omitted scalar fields inherit discovered defaults, explicit false/0 override them. `steamAppId` must match the filename/discovered app; executable, launch args, install path, ID and advanced Steam tracking remain discovery-owned. Relative custom images resolve from `SteamGames`; invalid custom images fall back to Steam art. Input/cursor edits are re-read at each launch into a separate game copy; reload refreshes card name/image/control overrides. Invalid JSON is reported and preserved, and blocks launch with a message rather than silently ignoring edits.
- Steam config cleanup runs on library reload only when the whole manifest inventory was readable. It removes only canonical `<AppID>-lc.json` regular files with valid matching `steamAppId` whose manifests are absent. Existing downloading/excluded manifests keep their configs; missing Steam, disconnected drives, malformed manifests and read failures disable deletion. Unrelated, mismatched, symlink or invalid files are retained. Steam manifests/caches remain read-only.
- Steam cards require the FullyInstalled manifest flag, no uninstalled/encrypted/locked/missing/corrupt/downloading/staging/uninstalling state, and an existing nonempty install directory. UpdateRequired alone is allowed. Duplicate AppIDs and Steamworks Common Redistributables are excluded; available offline `appinfo.vdf` metadata filters to game/demo/mod types and supplies controller support. Missing/unknown metadata falls back to manifest discovery (so unusual installed tools may appear in that case); unknown control support uses `controls: -1` to hide speculative input icons. Known Steam metadata maps `full` to controller-first (`0`), `partial` to both (`2`), and absent/other support to keyboard/mouse (`1`). These values describe Steam’s couch-play metadata, not per-device compatibility. The library/config inventory is refreshed on launcher reload, not continuously while Steam installs/uninstalls games; launch-time preparation lets an existing installed card wait for its ongoing update, while fresh discovery still excludes incomplete/actively updating installs. Existing cards may launch through Steam while updating; Steam owns completion before Play. AppID, manifest filename, installed directory identity and nonempty files remain required.
- Steam artwork prefers landscape headers/hero images for the 16:9 grid, with portrait capsules as a local fallback. Flat `<AppID>_*.jpg` and `<AppID>/<hash>/*.jpg` cache layouts are supported. If needed, Steam's CDN header is downloaded with an 8-second timeout/8MiB limit into `cache/thumbnails/steam-artwork`, validated, then passed through normal hash-based thumbnail generation. An unavailable image leaves the game listed with the Steam icon; no Steam cache/manifest is modified and no account API key is needed.
- Steam game cards use `TrackModeSteamGame` with `AdvancedTracking: true`. Every game launch activates Steam using `-gamepadui -fullscreen steam://run/<AppID>` so DRM, launch options, and first-run setup remain Steam-managed. A Job Object around the short-lived request process would miss an existing-client handoff: instead, same-session processes under the selected install directory are discovered every 250ms, verified through native handles, and attached to a dedicated game job; job members and verified descendants outside that directory are retained. Steam/client helpers are excluded. Failed job assignments retain handle/lineage tracking, with errors logged. Game-only job termination plus verified handle termination implements Start+Back without terminating Steam or other library games. There is no kill-on-close policy. Request exit does not complete the game session and the PID channel publishes the real game's first visible window for startup focusing.
- Steam diagnostic trap: generic launcher `game process started`/`game process exited` lines use `steamGameProcess.PID()` (the short-lived Steam activation PID), not the actual game executable PID. Use `Steam game process attached`, `Steam game first window`, `gamePIDs`, native process-exit records and tracking completion to interpret game activity. A successful activation-command exit only confirms command completion; it does not prove the game's Steam API initialized. Older logs emitted tracking lines only on PID changes, so `visible=false` at those changes cannot prove there was never a visible game window.
- Correlated `CrashReportClient.exe` and `crashpad_handler.exe` processes stay in the game's native handle/job/kill set, but `steamGameCrashHelper` and `steamGameProcess.activityPIDs` exclude them from visible-window handoff, activity counts and install-path stale-lock checks. A reporter window cannot dismiss the launch panel as a successful game opening, and helpers alone cannot prolong the running game's ten-second handoff grace. Startup retains its bounded UI-free grace; helper presence does not itself produce a crash error or shorten an unobserved launch. `pids` diagnostics include all correlated processes, while `gamePIDs` show those used for lifecycle timing. Helpers are logged on attachment; inherited job children remain available to Start+Back. Do not globally exclude these children from correlation/job cleanup or treat normal Crashpad startup as proof of a crash. Windows job/kill coverage includes both helpers and is not run. References: https://dev.epicgames.com/documentation/en-us/unreal-engine/crash-reporting-in-unreal-engine; https://chromium.googlesource.com/crashpad/crashpad/+/main/doc/overview_design.md.

Only known updates prompt `chooseSteamLaunch` with Open in Steam/Update in Steam/Back. `SteamLaunchAction(id, action)` atomically accepts one current ID/phase choice; no direct/silent choice or live rescue exists. Open in Steam uses the same game activation as every other card. Update in Steam opens Big Picture and `steam://nav/games/details/<AppID>` without Play; the user chooses Steam’s Update button. Exiting Big Picture returns with downloads Steam-owned and no automatic Play afterward. Navigation remains best-effort; the game can be selected manually if routing fails. Steam may pause downloads while playing according to its own settings.

No machine-local setup markers are read or written.

Steam itself does not retain a running card session after game exit. The old silent startup/update inactivity budgets were removed; pre-game UI lifetime owns waiting and Steam shows update/sign-in/EULA progress. Separate UI trackers retain verified handles and close after handoff/failure/completion; they are never part of the game kill job. Visible sign-in/update dialogs remain usable. A closed client is not restarted, no Steam/game process is killed, and no persistent settings or registry values change. The Big Picture-close command is asynchronously reaped/logged. The launcher should not lower the Windows display mode because borderless/windowed games can inherit that mode or render incorrectly when they try to use native resolution.
- `assets/loading-space.png` is embedded in the Go executable, then extracted to `cache/assets/loading-space.png` on startup. `ExtractEmbeddedFile` compares the cached bytes with the embedded image and refreshes changed content; the old cached JPEG is unused. The native wallpaper code still receives a file path because Windows GDI+ loads the PNG from disk; deployments do not need a separate wallpaper beside `stagebox.exe`. Keep the embed source, extraction target and startup fallback filename in sync when changing the native asset. The frontend library wallpaper is a separate Vite asset and must retain its “PLAY STARTS HERE” subtitle.
- `KillRunning` kills the tracked game process tree on Windows via hidden `taskkill /T /F`, with a direct process kill fallback. This matters for launchers that spawn child game processes.
- The normalized controller bridge and keyboard bridge emit Wails events and retain pause/resume behavior around games, Steam/RetroBat and pairing. Windows uses SDL3 mapped gamepads first, with the prior XInput/`winmm` fallback when SDL is unavailable or has no mapped pad. See the SDL3 section for ownership, mapping, hotplug and count rules.
- During game launch, the cursor is forced visible only when `showCursor` is true. The Windows cursor helper centers the pointer and injects a tiny synthetic mouse move so mouse-less systems can still materialize the cursor. For games without `showCursor`, the launch path temporarily replaces common Windows system cursors with transparent cursors and reasserts hidden cursor state briefly while the game window settles; system cursors are restored on game exit, startup, shutdown, restart, and debug exit. The launcher WebView also forces `cursor: none` in CSS so its pointer stays hidden even if Windows has a visible cursor. Card selection styling must come from `.gp-focus` or keyboard focus, not `.card:hover`, because invisible cursor position can otherwise make a second card look selected. `keyMap.mouse` can still move the OS cursor, but it does not make the cursor visible by itself. On game exit, mapped inputs are released, the cursor is moved to `(0,0)`, and the cursor is hidden before the launcher window is restored so the grid does not reopen with a hovered card.
- The normalized controller Start button opens the centered tools menu directly; B closes the menu. Holding Start+Back for about 700ms emits the `KILL` command before launcher/game input modes, so it also works while a game key-map is active.
- When `Bluetooth Pair` opens `DevicePairingWizard.exe`, the launcher hides, the controller bridge enters pairing keyboard mode, and the wizard is repeatedly foregrounded while visible. D-pad sends normal arrow keys, left stick left/right cycles dialog focus with Shift+Tab/Tab semantics, A sends Enter, and B sends Esc. Launcher navigation events are suppressed until the wizard window closes; before restoring the launcher the cursor is moved to `(0,0)` and hidden.
- Bluetooth pairing now uses the Windows pairing wizard bridge for the user-facing flow because it reaches the same shell/device-association path as Explorer. The legacy auto-pair API and abandoned WinRT helper were removed; `internal/platform/bluetooth` now provides Bluetooth state, bring-up, and connected-device detection. Keep Windows-only code behind `//go:build windows` and add or update matching stubs for other platforms.
- `App.ExitLauncher` has two modes. In debug mode the menu labels it `Debug - Exit Launcher` and it only quits the current Wails process so the Windows service loop can relaunch it without creating a duplicate instance. In normal mode the menu labels it `Exit to Windows`; the backend writes `exit-to-windows.flag`, starts `explorer.exe`, and quits. `custom_scripts/svc.vbs` consumes that flag after the launcher exits, deletes it, starts Explorer, and stops its relaunch loop for the current session.
- `App.OpenBluetoothPairing` is exposed as the first menu item, `Bluetooth Pair`. It opens `DevicePairingWizard.exe` to use the same Windows pairing path that Explorer/Settings uses.
- `custom_scripts/install-stagebox.ps1` is the preferred elevated setup entry point for a Windows kiosk. Run it as Administrator from a staging folder containing `stagebox.exe` and the helper scripts. It creates `C:\launcher`, copies runtime files (`stagebox.exe`, `svc.vbs`, `systemsvcs.ps1`, and `elevated-PS.cmd`) but not the installer itself, verifies `C:\launcher\stagebox.exe` exists before registering shell/autologon, writes `config.json` without a UTF-8 BOM with `gamesRoot` defaulting to `C:\games` and `debug: true` unless skipped, removes legacy helper scripts and the old `launcher.exe` name when possible, logs installation output to `installation.log` including account/SID/profile diagnostics, and derives a short local username such as `gamerX` from the current Windows identity for SMB share permissions, the user logon task, and AutoAdminLogon prompts. Shell registration still targets the loaded user hive through `HKCU` and explicit `HKEY_USERS\<sid>` to avoid ambiguity. It enables/starts Wi-Fi and Bluetooth-related services, removes every existing scheduled task under `\Launcher\`, registers `\Launcher\StageBox-EnsureSystem` as a SYSTEM startup task, registers `\Launcher\StageBox-EnsureUser` as a current-user logon task with ScheduledTasks `RunLevel Limited`, and routes both tasks through `wscript.exe //B //Nologo C:\launcher\svc.vbs systemsvcs` so the PowerShell service primer runs hidden. It optionally writes the current user's shell to `svc.vbs`. AutoAdminLogon must use a nonblank password; a blank password skips that setup to avoid broken login state. Prefer extending this installer over adding new one-off setup scripts.
- `custom_scripts/systemsvcs.ps1` is the sole service/adapters primer. Scheduled tasks run it at startup/logon; it starts `WlanSvc`, Bluetooth-related services, per-user Bluetooth service, turns the Bluetooth radio on when possible, enables candidate Wi-Fi adapters, and optionally logs `netsh wlan show drivers/interfaces`.
- `App.ScanWifiNetworks` and `App.ConnectWifiNetwork` back the `Wi-Fi Networks` overlay. On Windows they use absolute hidden `netsh.exe` commands and do not try to force-start `WlanSvc` from the non-elevated launcher; instead scan/connect retry briefly when `netsh` reports `wlansvc is not running`, because Windows can bring the service back asynchronously. Scanning runs `netsh wlan show networks mode=bssid` with a plain `show networks` fallback and annotates networks as saved when Windows has either an SSID-named profile or a StageBox profile for that SSID. Saved secure networks connect without showing the password field. Password connections create temporary WPA2 profile XML using a StageBox-owned profile name (`StageBox-<ssid-hash>`) so existing policy/all-user profiles named after the SSID are not overwritten, try current-user then all-user profile scope, then fall back to connecting an existing SSID-named profile. `systemsvcs.ps1` retries Wi-Fi autoconnect at startup/logon after ensuring `WlanSvc`, first for visible `StageBox-*` profiles and then for other saved WLAN profiles; the user logon scheduled task runs least-privilege so current-user WLAN profiles are visible. Adapter priming skips Wi-Fi Direct virtual adapters and Xbox Wireless Adapter devices, and only calls `Set-PnpDevice` when that cmdlet exists. Failed connects log `netsh wlan show interfaces/drivers/profiles` diagnostics. This avoids relying on Windows shell WiFi flyouts, which may no-op in kiosk/shell-replacement mode. `WlanSvc` should still be enabled/started by `install-stagebox.ps1` and `systemsvcs.ps1`. If scans fail with `OpenService FAILED 5` or `wlansvc is not running`, rerun `install-stagebox.ps1` as Administrator on the Windows box. If scans fail with `no wireless interface detected`, inspect `svc.log` service diagnostics for missing/disabled Wi-Fi drivers or adapters.
- The pairing wizard lifecycle is guarded against reentry. After the wizard window closes, the launcher terminates a lingering `DevicePairingWizard.exe` process before restoring itself so quick reopen attempts do not wait on Windows' delayed process cleanup.
- `status:update` includes `controllerCount`, sourced from the controller poller's atomic snapshot of opened SDL gamepads (or native XInput/WinMM inventory while fallback is selected). The Bluetooth indicator is slashed gray when Bluetooth is off/disabled/unknown, plain gray when Bluetooth is on but no Bluetooth controller is connected, and green when a Bluetooth controller is connected. The Wi-Fi indicator is slashed gray when no Wi-Fi interface is available, gray when Wi-Fi is available but disconnected, and green when connected.

- `make help` prints the full build prerequisites, Fedora's `sudo dnf install dotnet-sdk-10.0` command and `DOTNET` executable-path override. `make virtual-helper-deps` validates Python 3.11+ and the selected SDK version (10+) before any helper-asset downloads; runtime-only or older SDKs fail with setup instructions. - `make build-linux` runs a Linux Wails build with the same tag.

## Development Hints

- Prefer existing patterns: Wails-bound methods on `App`, domain packages under `internal/platform`, plain JS modules under `frontend/src/features`.
- Treat `config.json` as local runtime configuration. Avoid hard-coding paths except where the Windows kiosk/bootstrap flow already requires fixed paths.
- Preserve build tags. Every new Windows-specific file should have `//go:build windows`; add a `!windows` stub when shared code calls it.
- Keep frontend state derived from backend events where possible. Existing event names are short and status-oriented.
- Be careful with UUID handling. Frontend passes IDs as strings; Wails currently maps them back into `uuid.UUID` parameters for methods such as `Launch`.
- Avoid broad changes under `vendor` unless explicitly updating vendored dependencies or local vendor patches.
- Logging should use `internal/logx` for app diagnostics. Existing direct `log.Println` calls remain, but new app-level diagnostics should usually go through `logx`.
- `jsonx.LoadJSONFile` rejects unknown JSON fields. When adding config or game metadata fields, update the Go structs first.
- `jsonx.LoadJSONFile` tolerates a UTF-8 BOM before strict JSON decoding. This is important for Windows-generated `config.json` files from older PowerShell flows.
- Do not assume Windows helper commands work on Linux. Non-Windows stubs intentionally return no-op or `"unknown"` behavior.
- Keep thumbnail filenames hash-based and include the thumbnail size/version in the filename. The source hash invalidates cache when source images change; the size suffix forces regeneration when thumbnail dimensions change.

## Common Feature Entry Points

- Add game metadata fields: update `internal/games/data.go`, adjust `internal/games/loader.go` if path resolution or derived data is needed, then update `frontend/src/main.js` rendering.
- Add thumbnail behavior: update `internal/games/thumbnails.go`, keep output URLs under `/game-thumbs/`, and avoid putting image bytes in Wails method return payloads.
- Add a topbar action: add the button in `frontend/index.html`, bind it in `frontend/src/main.js`, and expose a Go `App` method if it needs backend behavior.
- Add controller behavior: update event emission in `internal/platform/controller/controller_windows.go` and handling in `frontend/src/features/controller.js`.
- Add a status indicator: add backend status data in `App.GetStatuses`, emit `status:update` when it changes, then render it in a frontend module.
- Add Windows integration: implement it under the relevant `internal/platform/*` package, call it from `app.go` or an `App` method, and create a matching stub file.
